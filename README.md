# AI-помощник для подготовки товарных описаний

Локальный HTTP-сервис для создания черновиков карточек
контрольно-измерительных приборов для B2B-интернет-магазина.

Принимает данные товара в JSON, передаёт их LLM через OpenRouter
и возвращает:

- SEO-заголовок до 70 символов;
- SEO-описание от 800 до 1200 символов;
- структурированный список характеристик;
- 3–5 поисковых запросов;
- коммерческий блок: кому подходит прибор и какие задачи решает;
- сведения о недостающих данных, вопросы и предупреждения.

Черновик требует проверки контент-менеджером перед публикацией.

## Стек

TypeScript, Node.js, Fastify, Zod, Vitest.
Для обращения к OpenRouter используется встроенный fetch.

Модель задаётся переменной окружения LLM_MODEL.
При подготовке примеров использовалась
nvidia/nemotron-3.5-super-vl:free.

## Установка и запуск

Окружение для запуска: Node.js 24 и npm.

Из корня проекта установите зависимости:

```bash
npm ci
```

Создайте файл конфигурации:

```bash
cp .env.example .env
```

Укажите в нём ключ OpenRouter:

```dotenv
OPENROUTER_API_KEY=ваш_ключ
LLM_MODEL=nvidia/nemotron-3.5-super-vl:free
PORT=3001
```

Запустите сервер:

```bash
npm run dev
```

Адрес сервиса: http://127.0.0.1:3001

Для генерации нужны интернет, действующий ключ и доступная
у провайдера модель. Доступность бесплатной модели и её лимиты
зависят от провайдера.

## Использование

Команды выполняются из корня проекта при работающем сервере.

Проверка запуска:

```bash
curl http://127.0.0.1:3001/health
```

Ожидаемый ответ:

```json
{ "status": "ok" }
```

Этот запрос проверяет приложение, но не соединение с LLM.

Генерация по первому товару:

```bash
curl --fail-with-body \
  http://127.0.0.1:3001/generate \
  -H 'Content-Type: application/json' \
  --data-binary @examples/product_1.input.json \
  -o /tmp/product_1.live.json
```

Генерация по второму товару:

```bash
curl --fail-with-body \
  http://127.0.0.1:3001/generate \
  -H 'Content-Type: application/json' \
  --data-binary @examples/product_2.input.json \
  -o /tmp/product_2.live.json
```

Ответы сохраняются отдельно от примеров в репозитории.

Для форматированного просмотра сохранённого ответа выполните команду ниже:

```bash
node --input-type=module -e '
import fs from "node:fs";
const data = JSON.parse(fs.readFileSync("/tmp/product_1.live.json", "utf8"));
console.log(JSON.stringify(data, null, 2));
'
```
Генерация недетерминирована. Новый ответ может отличаться
от сохранённого примера.

### Генерация для своего товара

Создайте файл `my-product.json` в корне проекта:

```json
{
  "name": "Название и модель прибора",
  "manufacturer": "Производитель",
  "specs": {
    "Название характеристики": "Значение",
    "Неизвестная характеристика": null
  },
  "description": "Исходные сведения: назначение, функции, фрагмент паспорта."
}
```

Замените значения своими данными. Состав характеристик произвольный.
Неизвестные значения можно передать как `null`.
Описание можно опустить, если сведения переданы в характеристиках.

При работающем сервере отправьте файл:

```bash
curl --fail-with-body \
  http://127.0.0.1:3001/generate \
  -H 'Content-Type: application/json' \
  --data-binary @my-product.json \
  -o my-product.output.json
```

Откройте `my-product.output.json` в редакторе.

`draft` означает, что подготовлен черновик.
`needs_input` означает, что нужно дополнить сведения.
Проверьте `missing_fields`, `questions` и `warnings`.

## Входные данные

POST /generate принимает объект:

```json
{
  "name": "Манометр показывающий DM 02",
  "manufacturer": "Манотомь",
  "specs": {
    "диапазон измерений": "0–1,6 МПа",
    "класс точности": "1,5",
    "присоединение": "G1/2",
    "диаметр корпуса": "100 мм",
    "питание": null
  },
  "description": "Прибор предназначен для измерения избыточного давления."
}
```

Значение характеристики может быть строкой, числом или null.

Правила обработки:

- Пробелы по краям строк удаляются.
- Пустые характеристики и null отображаются как «данных нет».
- Числовой ноль считается известным значением.
- Пропущенные строковые поля получают пустые значения.
- Пропущенный specs становится пустым объектом.
- Неизвестные поля и неподходящие типы отклоняются.
- Вход ограничен по размерам строк и количеству характеристик.

Если отсутствует название либо одновременно отсутствуют
описание и непустые характеристики, приложение запрашивает
данные без вызова LLM.

Отсутствие производителя не блокирует генерацию, но отмечается
в missing_fields.

## Выходные данные

При успешной генерации возвращается status: "draft".

| Поле             | Назначение                             |
| ---------------- | -------------------------------------- |
| seo_title        | Заголовок до 70 символов               |
| seo_description  | Описание на 800–1200 символов          |
| characteristics  | Массив объектов с полями name и value  |
| search_queries   | От 3 до 5 поисковых формулировок       |
| commercial_block | Назначение прибора и задачи покупателя |
| missing_fields   | Отсутствующие или пустые поля входа    |
| questions        | Вопросы для уточнения                  |
| warnings         | Предупреждения                         |

Если данных недостаточно, возвращается status: "needs_input".
Текстовые поля карточки равны null, search_queries пуст.
Переданные характеристики и список недостающих полей сохраняются.

Модель также может запросить уточнение, если фактов недостаточно
для достоверного описания нужной длины или обнаружены противоречия.
Такая оценка модели не является гарантированной проверкой полноты.

Поисковые запросы это предложенные формулировки, а не результат
исследования частотности.

## Ошибки

| HTTP-код | Ситуация                                                                  |
| -------- | ------------------------------------------------------------------------- |
| 400      | Синтаксически некорректный JSON                                           |
| 422      | Неверные типы, неизвестные поля или другие нарушения схемы                |
| 502      | Ошибка генерации, включая сбой API или невалидный ответ после исправления |

Недостаток исходных сведений возвращается с HTTP 200
и статусом needs_input.

Ошибку разбора JSON формирует Fastify. Ошибки валидации входа
возвращаются с кодом INVALID_INPUT. Ошибки генерации
с кодом GENERATION_FAILED.

## Устройство решения

- src/app.ts — маршруты и HTTP-ответы.
- src/schemas.ts — схемы входа и ответа модели.
- src/service.ts — оценка полноты, проверка ответа и исправление.
- src/prompts.ts — системный промпт и сообщения с данными товара.
- src/llm.ts — HTTP-клиент OpenRouter.
- src/config.ts — проверка переменных окружения.
- src/server.ts — запуск приложения.
- tests/ — автоматические тесты.
- examples/ — источники, входы, результаты и ручные проверки.

Порядок обработки:

1. Проверить входные данные.
2. Определить пропуски и сформировать характеристики.
3. Передать модели системный промпт и JSON товара.
4. Разобрать ответ как JSON и проверить схему, длины и количество полей.
5. При нарушении формата выполнить одну попытку исправления.
6. Добавить характеристики из входа и вернуть результат.

Таймаут каждого запроса к провайдеру — 30 секунд.
При исправлении выполняется второй запрос с отдельным таймаутом.
При ошибке API автоматический повтор не выполняется.

## Промпт и принятые решения

Системный промпт ограничивает модель сведениями из входного JSON.
Запрещены выдуманные характеристики, неподтверждённые преимущества,
расшифровка маркировок через знания модели и расширение областей
применения.

Поля товара передаются как данные. Модель получает отдельное
указание не выполнять инструкции, содержащиеся внутри этих полей.

Для состояний draft и needs_input заданы отдельные форматы ответа.
Если фактов недостаточно для нужного объёма, модель должна запросить
уточнение вместо заполнения текста выдумками.

Характеристики формируются кодом из specs. Это сохраняет исходные
значения в структурированном списке. Свободный текст генерируется
моделью и требует отдельной смысловой проверки.

Проверка ответа через Zod контролирует формат и размеры.
При ошибке модели передаются замечания валидации и запрос
на исправление. Количество попыток ограничено двумя,
чтобы избежать бесконечных повторов.

Для MVP выбран JSON API. Такой вариант соответствует заданию
и позволяет сосредоточиться на генерации и обработке данных.

## Примеры и источники

Подготовлены два товара ОВЕН:

1. МК110-224.8Д.4Р [М01] — комбинированный модуль ввода/вывода.
2. СВ01-24.Н.Р — счётчик времени наработки оборудования.

Для каждого товара сохранены:

- product_N.source.xml — фрагмент исходного фида;
- product_N.input.json — подготовленный вход;
- product_N.output.json — фактический ответ генерации;
- product_N.review.md — замечания ручной проверки.

По согласованию с работодателем товары выбраны из предложенного
XML-фида. В выбранных offer отсутствовали технические характеристики
и описание, поэтому входы вручную дополнены проверенными сведениями
со страниц соответствующих товаров.

Учитывались различия исполнений. Неоднозначные сведения
не переносились в подготовленные входы.

Это ручная подготовка данных для демонстрации.
Сервис не загружает сайты или XML-фид. Модель получает только JSON.

Ссылки и пояснения находятся в examples/sources.md.

Дополнительно сохранён пример product_incomplete:
из второго товара удалён производитель, степень защиты заменена
пробелами, масса — null. Результат и его ограничения описаны
в examples/product_incomplete.review.md.

Сохранённые примеры отражают отдельные запуски и этапы уточнения
промпта. Они не являются гарантией идентичного результата
при повторном запросе.

## Проверка

```bash
npm test
npm run typecheck
```

Автоматические тесты проверяют:

- корректные и некорректные входы;
- синтаксически неправильный JSON;
- пустые поля и сохранение числового нуля;
- перенос исходных характеристик;
- ограничения длины ответа;
- запрос уточнений;
- попытку исправления и остановку после второй ошибки;
- обработку сбоя генерации.

В тестах модель подменяется: они не требуют ключа,
не расходуют запросы и не проверяют реальное качество LLM.

Вручную проверены реальные запросы для двух полных товаров
и товара с пропусками. Также проверены пустые поля,
неправильный тип specs и незакрытый JSON.

## Сложности и ограничения MVP

Основная сложность — достоверность свободного текста.
Модель может сохранять числовые характеристики, но расширять
смысл исходных утверждений.

В ходе проверки обнаружены:

- вывод условий эксплуатации из IP20;
- расширение удобства монтажа до обслуживания;
- добавление бытового применения;
- замена условий запуска словами «дистанционный/локальный»;
- интерпретация количества включений прибора как частоты
  стартов оборудования;
- формулировка, создающая впечатление обязательности датчика.

После уточнений промпта часть ошибок исчезла в последующих
ответах. Это наблюдение на отдельных примерах, а не гарантия
отсутствия выдумок.

Также встречались опечатки, ошибки согласования и пропуск
обозначения исполнения в заголовке. Замечания сохранены
в review-файлах.

Полнота проверяется по переданным полям. Отраслевой перечень
обязательных характеристик для каждого типа прибора не реализован.
Приложение не определяет самостоятельно все отсутствующие
технические параметры.

Автоматическая сверка каждого утверждения с источником
не реализована. Защита от инструкций внутри данных основана
на промпте и не гарантирует устойчивость ко всем случаям.

В рамках MVP не реализованы веб-форма, импорт источников,
история генераций, пакетная обработка и деплой.

При ручной проверке prompt injection одна из трёх атак
оказалась успешной: имитация системного сообщения в описании
изменила commercial_block. Подробности приведены
в examples/prompt_injection.review.md.
